    • 설계 판단 — 발송량 0을 실패율 0%로 그리지 않는다. SMS 물량의 47.4%가 오전 한 배치에 몰려 있어, 그 배치가 실패하면 발송 자체가 없어 실패율에는 아무것도 잡히지 않는다

    • 발송 배치가 콘텐츠 행을 잡은 채 커밋하지 않아 상세 조회가 lock wait timeout 으로 실패했다. 원인을 트랜잭션 길이가 아니라 완료 표시의 커밋 시점으로 좁혀 해당 갱신을 건별 커밋으로 분리
    • 반복되던 락 경합 timeout 주 2~3회 → 0건 (발송 대상 평균 1천 명 규모)
  • 2026 · 배치의 외부 호출을 worker 로 분리
    • 맥락 — 일배치가 병원 도메인으로 HTTP 요청 약 440건을 순차로 보내 대표 이미지를 추출하면서 배치 스레드를 오래 점유했다. APM 으로 한 실행을 분해해 이 구간이 22초 이상임을 확인했다
    • 외부 추출을 별도 worker 로 비동기 이관하고, 요청 원장 테이블과 결과 반영 잡을 분리한 2-잡 구조(enqueue / reconcile)로 재구성. 멱등 처리와 SSRF 가드를 넣어 재실행과 외부 호출을 안전하게 함
    • 추출 92.5초 → 13.3초 (약 6.94배, stag APM 실측). 같은 기간 미배포 상태의 운영 환경은 149초대를 유지해 배포 효과임을 대조로 확인
  • 2026 · 빨라진 원인을 벤치마크로 규명
    • "Node 라서 빠르다" 는 해석이 맞는지 확인하기 위해 4변형(Java 동기·비동기 / Node 동기·비동기) × 페이지 수 × 동시성 6단계 × 5회, 420행을 측정. 추출 로직과 mock 서버를 고정해 동시성만 변수로 남김
    • 언어는 변수가 아니었다 — Java 동기와 Node 동기가 0.6% 차이. 순차를 비동기로 바꾼 것만으로 90~105배였고, 같은 동시성 모델이면 언어가 달라도 결과가 같았다
    • Node 비동기가 같은 처리량에서 CPU 를 약 37.7% 적게 썼다. worker 를 분리한 이유를 "언어" 가 아니라 동시성·격리·CPU 효율로 정리 (mock 서버 기준)
  • 2026 · 실패로 잡히지 않는 누락을 관측 지표로
    • 실패·폴백·stuck 카운트가 모두 0인데 적용률만 86~93% 에서 14~27% 로 떨어지는 구간을 발견. 요청 원장 11일치를 복원해 원인이 추출 결과가 빈 값으로 돌아오는 것임을 확인했고, 트리거는 worker 인스턴스 교체 시점과 일치했다
    • 로그 보존 기간이 3.5일뿐이라 3일 창만 보면 평균 76% 로 건강해 보였다. 영구 보존되는 원장으로 소스를 바꿔 11일 평균 54% 를 드러냄
    • 적용률(applied/processed)과 추출 실패율을 알람 지표로 설계. 대상 페이지 5,057건 중 4,825건에 썸네일이 적용된 상태(95.4%)
