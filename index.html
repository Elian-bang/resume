  • 2026 · CRM 알림톡 발송 — 초기 구현을 세 번 되돌림 (STAG 반영, 운영 배포 전)

    • 되돌림 1 — 결과 판정을 위해 발송을 동기 REST 로 바꿀 때 처음에는 모든 호출자를 한꺼번에 전환했다. OTP 와 기존 알림까지 큐의 버퍼링을 잃는 전역 변경이었고 합의된 범위도 아니어서 되돌렸다. 결과 판정이 필요한 CRM 발송만 동기로 두고 나머지는 큐를 유지
    • 되돌림 2 — 발송 결과를 성공·실패 두 값으로 판정했다가, "안 나갔다" 와 "나갔는지 모른다" 를 구분하지 못해 개발 환경에서 같은 문자가 반복 발송됐다. SENT / NOT_SENT / UNKNOWN 3분류로 바꾸고 재시도는 안 나간 것이 확실한 경우만 하도록 제한. 모르는 건은 자동 복구하지 않고 사람이 판단하게 남겼다
    • 되돌림 3 — 캠페인 전체를 한 트랜잭션으로 묶었더니 1건 실패가 이미 나간 나머지의 결과 기록까지 롤백시켰다. 예약 1건 = 트랜잭션 1개로 격리
    • 사고 건수는 처음 48회로 보였지만 실제로는 9회였다. 무효로 판정한 실험 2건도 기록에 남겼고, QA 점검표 104항목을 만들었다
    • 배포 범위 — 기다리는 병원이 있어 범위를 쪼개서라도 일정을 앞당기자는 제안이 있었으나, 전송 결과를 확인할 화면 없이 발송 기능만 먼저 내보내는 것은 부적절하다고 보고 전송 내역과 함께 내자고 했다. 일정은 지키고 범위를 묶는 쪽으로 정리
  • 2026 · 집계에서 빠져 있던 실패를 드러냄
    • 발송 결과는 DB에 있었지만 조회 화면이 없어, 물량은 매번 SQL로 확인했고 실패는 고객 문의로 알았다. 13개월치를 직접 조사했다
    • 성공 판정이 틀려 있었다 — 벤더가 거절한 141건도 상태가 COMPLETED 였다. 판정 기준을 상태값에서 응답 코드로 바꿨다. 상태 허용 목록에 빠져 있던 실패 242건도 13개월간 모든 집계에서 누락돼 있었고, 목록 밖 값을 세는 감시 쿼리를 짝으로 두는 규칙으로 정리
    • 결과 콜백을 못 받아 미확정으로 남은 건이 435건, 가장 오래된 것은 442일 경과 상태였다
    • 선택한 이유 — 발송량이 0이면 실패율도 0%로 보일 수 있다. SMS 물량의 47.4%가 오전 한 배치에 몰려 있어, 그 배치가 실패하면 실패율만으로는 문제를 찾을 수 없다

  • ② 빨라진 원인을 벤치마크로 규명

    • Java 동기와 Node 동기는 0.6% 차이였다. 언어보다 순차 처리와 비동기 처리의 차이가 컸다
    • mock 서버 기준으로 Node 비동기는 같은 처리량에서 CPU를 약 37.7% 적게 썼다. worker를 나눈 이유는 언어가 아니라 동시성, 격리, CPU 효율로 정리했다
  • ③ 실패로 잡히지 않는 누락을 관측 지표로
    • 실패·폴백 카운트는 모두 0인데, 썸네일 적용률은 86~93%에서 14~27%로 떨어졌다. 11일치 요청 기록에서 worker가 빈 값을 자주 돌려준 것을 찾았다
    • 적용률 하락은 worker 인스턴스 교체 시점과 겹쳤지만, 기술적 원인은 확인하지 못했다. 로그 3일치만 보면 평균 76%로 보였지만, 11일 기록으로는 평균 54%였다
    • 전체 요청 중 썸네일이 적용된 비율과 추출 실패율을 알람으로 삼았다. 대상 페이지 5,057건 중 4,825건에 썸네일이 적용된 상태(95.4%)

    • 문자·알림톡·자동화가 같은 값(전송일, 담당의사·예약일 변수)을 서로 다른 이름으로 저장하고 있어 한 이름 체계로 맞춤. 운영 데이터 이관을 백업 → 적용 → 검증 세 단계로 나누고 "옛 값 0, 충돌 0, 알림톡 문구 변경 0" 을 합격 기준으로 둠. 개발 환경에서 충돌 46건을 먼저 찾아 운영 적용 전에 대응

    • 선택한 이유 — 새 인덱스를 추가하지 않고 기존 복합 인덱스를 활용해 쓰기 성능을 유지
    • 리마인드 알림 조회 응답 시간을 약 5~6초에서 300~400ms로 단축
  • 2025 · 조회 방식 셋을 부하테스트로 비교해 선택
    • 문제 — 통계의 인기 페이지 목록이 링크만 보여 어떤 페이지인지 알기 어려웠다. 대표 이미지를 보여 주기 위한 조회 방식을 정해야 했다
    • 요청 때 외부 페이지를 읽는 방식, 테이블에 저장해 두는 방식, 저장 후 Redis로 캐싱하는 방식을 같은 조건에서 비교. Redis 자료구조도 String과 Hash로 나눠 비교
    • 외부 페이지를 직접 읽는 방식은 170건이 모두 타임아웃이었다. 저장 방식으로 바꾸자 실패가 사라졌고, Redis를 더하자 평균 633ms → 399ms가 됐다. 동시 사용자 10명 조건에서 Hash 이점은 없어 String을 선택
  • 2026 · 푸시 발송 락 경합 대응
    • 발송 배치가 콘텐츠 행을 잡은 채 커밋하지 않아 상세 조회가 lock wait timeout으로 실패했다. 완료 표시가 커밋되는 시점을 원인으로 확인해 해당 갱신을 건별 커밋으로 분리
    • 반복되던 락 경합 timeout 주 2~3회 → 0건 (발송 대상 평균 1천 명 규모)
